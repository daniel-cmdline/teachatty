01

Visão geral

O teachat é um chat de terminal para desenvolvedores e sysadmins. Um servidor guarda as salas em memória e repassa as mensagens; cada pessoa roda o cliente no próprio terminal, entra numa sala e conversa. Foi feito para rodar no servidor da própria empresa.

Estado: desenvolvimento inicial. Funciona para conversar entre máquinas, mas ainda sem criptografia (o tráfego é ws:// aberto) e com mudanças incompatíveis a caminho. Use só em rede confiável. Veja as limitações.

servidor
cmd/server. Escuta na porta 7347, mantém as salas em memória, repassa cada mensagem para os outros membros da sala.
cliente
cmd/client. Num terminal, abre a tela cheia: mensagens em cima, caixa de digitação embaixo. Num pipe (comando | teachat), envia cada linha e sai.
sala
Um nome qualquer. Entrar numa sala que não existe cria a sala; quando o último membro sai, ela deixa de existir. A exceção é a local, a sala padrão: nasce com o servidor e existe enquanto ele rodar. Quem não escolhe sala cai nela.
alias
O nome que aparece na frente das suas mensagens: daniel: oi. Por padrão, o seu usuário do sistema. Não é verificado.
mensagem
Uma linha de texto. Vai só para quem está na sala naquele momento: não há histórico.
02

Começando

Requisitos: Go 1.27 ou mais novo, um terminal com UTF-8 e a porta 7347 liberada na máquina do servidor.

Rodar a partir do código

git clone https://github.com/daniel-cmdline/teachat.git
cd teachat

# servidor
go run ./cmd/server
# teachat-server listening on :7347 · default room: local

# cliente, em outro terminal: sem flags, entra na sala local
go run ./cmd/client

# ajuda, nos dois
go run ./cmd/client -h
go run ./cmd/server -h

Outra máquina na rede

Aponte o cliente para o endereço do servidor e garanta que a porta 7347 está aberta no firewall dele:

go run ./cmd/client --server 192.168.0.10:7347

Para usar outra porta, ou escutar só numa interface, o servidor tem --addr. O cliente aponta para o mesmo endereço com --server:

go run ./cmd/server --addr :9000
go run ./cmd/client --server 192.168.0.10:9000

Gerar os binários

O go build nomeia o binário pela pasta (client, server). Para ter o nome teachat:

go build -o teachat ./cmd/client
go build -o teachat-server ./cmd/server

./teachat-server
./teachat --room dev --alias daniel

Modo pipe

Quando o stdin não é um terminal, o cliente não abre a tela. Ele envia cada linha da entrada para a sala, repete a linha no seu terminal (como o tee) e sai quando a entrada acaba.

make 2>&1 | teachat --room ops              # a saída do build vai para a sala
uptime | teachat --room ops                  # uma linha e sai
tail -f /var/log/app.log | teachat --room ops   # transmite até o Ctrl+C
uma mensagem por linha
Cada linha vira uma mensagem alias: linha na sala. Sem agrupar: um log de 5000 linhas são 5000 mensagens.
eco
Toda linha aparece no seu terminal também, inclusive as vazias. Linhas vazias não vão para a sala.
tamanho
Até 1 MB por linha, o limite do servidor. Uma linha maior é recusada: o pipe para e sai com código 1, dizendo message too big.
a sala
O que os outros mandam enquanto o pipe roda não aparece; é lido e descartado.
nunca abre a tela
Seguro em scripts, CI e cron: ninguém precisa apertar Ctrl+C no fim.
sem histórico
Se ninguém estiver na sala, as linhas se perdem.
04

Referência do servidor

Uma flag, --addr, além do -h (help também mostra a ajuda, e qualquer outro argumento mostra a ajuda e sai com código 2, sem subir o servidor). Ele escuta em :7347, em todas as interfaces, e expõe um único endpoint.

Flags

flagpadrãodescrição
--addr:7347onde escutar, host:porta. Sem host, todas as interfaces: --addr :9000. Com host, só aquela: --addr 10.0.0.5:7347 escuta só na rede interna

Porta ocupada ou endereço inválido: o servidor sai com o erro (address already in use, missing port in address) e código 1, sem anunciar nada antes.

Endpoint

GET /ws?room=<sala>&alias=<alias>   upgrade para WebSocket
room
Nome da sala. Qualquer texto. Não existe → é criada. Ausente ou vazio → sala local.
alias
Nome de quem conecta. Qualquer texto, inclusive vazio. Não é validado nem precisa ser único.
origem
Aceita conexões de qualquer origem (CheckOrigin sempre retorna verdadeiro).

Mensagens

cliente → servidor
Um frame de texto com a mensagem pura: oi.
servidor → cliente
Um frame de texto com o alias na frente: daniel: oi. Vai para todos os membros da sala, menos quem enviou.
tamanho
Até 1 MB por mensagem (maxMessage). Acima disso, o servidor responde com close 1009 (message too big) e fecha só aquela conexão; a sala segue normal.
histórico
Nenhum. A sala é uma lista de conexões, não guarda mensagens.

Ciclo de vida das salas

entrar
Se a sala não existe no mapa, é criada, e a conexão vira membro.
sair
Quando a conexão termina, sai da sala. Sala vazia é apagada do mapa, menos a local.
sala padrão
A local já está no mapa quando o servidor sobe e nunca é apagada. É para onde vai quem não pede sala.
estado
Tudo em memória. Reiniciar o servidor derruba todo mundo e apaga todas as salas.

Saída no terminal

Imprime teachat-server listening on :7347 · default room: local ao subir e registra erros de upgrade com log. Se a porta estiver ocupada, sai com o erro do ListenAndServe.

05

Arquitetura

O teachat são dois binários, um servidor e um cliente, que conversam por WebSocket. O código próprio tem cerca de 380 linhas porque se apoia em camadas que já fazem o trabalho pesado. Cada mensagem desce por todas elas de um lado e sobe por todas do outro.

As camadas

tview + tcellSó no cliente. Põe o terminal em modo raw, lê cada tecla, desenha a tela (área de mensagens, caixa de digitação, bordas) e devolve o terminal ao normal na saída.biblioteca

O caminho de uma mensagem

Daniel e Mateus estão na sala dev. Daniel digita oi e aperta Enter. A versão animada, passo a passo, está no site.

  1. Tecla a tecla

    O terminal do Daniel está em modo raw. O tcell entrega cada tecla ao loop de eventos do tview, e o texto fica na caixa de digitação. No Enter, o cliente chama send, mostra daniel: oi na própria tela e limpa a caixa (cliente por dentro).

  2. Frame mascarado

    WriteMessage monta um frame de texto mascarado e o kernel envia pelo socket TCP (anatomia de um frame).

  3. A goroutine do Daniel no servidor acorda

    Ela estava parada no ReadMessage. Recebe oi e monta daniel: oi (servidor por dentro).

  4. Broadcast na sala

    Trava só o mutex da sala dev e escreve em cada membro, menos no próprio Daniel (travas).

  5. A goroutine de recebimento do Mateus acorda

    Chama screen.Print, que põe a linha na fila do tview. O loop de eventos escreve a mensagem e redesenha, sem tocar no que o Mateus está digitando.

06

A conexão: TCP, depois HTTP, depois WebSocket

Antes de qualquer mensagem, o cliente abre uma conexão que passa por três protocolos, um em cima do outro. O WebSocket começa como uma requisição HTTP comum e, quando o servidor responde 101, aquele mesmo socket TCP deixa de falar HTTP para sempre.

Das flags até a URL

O usuário nunca digita URL. O cliente monta a URL a partir das flags, e o servidor lê os parâmetros dela.

você digita

teachat \
  --room dev \
  --alias daniel
→

cliente monta

ws://localhost:7347
  /ws?alias=daniel
     &room=dev
→

servidor lê

r.URL.Query()
  .Get("room")  // dev
r.URL.Query()
  .Get("alias") // daniel

No servidor, tudo isso acontece dentro de uma linha: upgrader.Upgrade(w, r, nil). No cliente, dentro de websocket.DefaultDialer.Dial(...).

A prova do Sec-WebSocket-Accept

O servidor pega a chave que o cliente mandou, cola nela um GUID fixo definido no RFC 6455, tira o SHA-1 e codifica em base64. O cliente faz a mesma conta e compara.

Isso não é segurança. Serve para provar que o servidor entende WebSocket de verdade, e não é um servidor HTTP qualquer ou um cache no meio do caminho respondendo por engano. O GUID é o mesmo em todo servidor WebSocket do mundo.

07

Anatomia de um frame

O TCP é um fluxo de bytes sem fronteiras: ele não sabe onde uma mensagem termina e a próxima começa. O WebSocket resolve isso colocando um cabeçalho de 2 a 14 bytes na frente de cada mensagem. É isso que o WriteMessage monta e o ReadMessage desmonta. Digite uma mensagem e veja os bytes exatos que vão pelo socket.

FIN + opcodeMASK + tamanhochave de máscaraconteúdo
byte 0
FIN=1 · RSV=000 · opcode=0001 (texto)
byte 1
MASK=1 · tamanho=2

Frames do cliente vão mascarados: cada byte do conteúdo passa por XOR com a chave de 4 bytes. Na vida real a chave é sorteada a cada frame; aqui ela está fixa em 37 fa 21 3d para o exemplo ficar estável.

Por que só o cliente mascara

A regra é do RFC: tudo que vai do cliente para o servidor precisa estar mascarado, e o que vai do servidor para o cliente, nunca. O motivo não é criptografia, já que a chave viaja junto com o frame. É proteção para proxies antigos: sem máscara, um JavaScript malicioso num navegador poderia montar bytes que um proxy leria como uma requisição HTTP e guardaria lixo no cache dele.

O tamanho em 7, 16 ou 64 bits

Até 125 bytes, o tamanho cabe nos 7 bits do byte 1. Com o valor 126, os 2 bytes seguintes dizem o tamanho real (até 65.535). Com 127, são os 8 bytes seguintes. Digite mais de 125 caracteres no campo acima para ver o cabeçalho crescer.

08

O servidor por dentro

Um processo só, várias goroutines. O loop de Accept do net/http recebe cada conexão TCP nova e faz go c.serve(...): a conexão ganha uma goroutine própria, que roda o handler de /ws pelo tempo que a pessoa ficar no chat.

goroutines vivas com três pessoas conectadas
main · loop do Acceptespera a próxima conexão chegarAccept()
handler /ws · danielconn = fd 5 · room = devReadMessage()
handler /ws · mateusconn = fd 8 · room = devReadMessage()
handler /ws · joãoconn = fd 9 · room = geralReadMessage()

Cada goroutine tem as próprias variáveis locais: conn, name, alias, msg. O que é compartilhado entre elas, o mapa rooms e cada *Room, precisa de trava.

/proc/PID/fd do servidor (medido)

4socket:[2305506] · porta 7347 escutando
5socket:[2306269] · conexão com o cliente 1
6anon_inode:[eventpoll] · o epoll do runtime
7anon_inode:[eventfd] · acorda o epoll
8socket:[2297779] · conexão com o cliente 2

Cada *websocket.Conn no mapa é, no fundo, um desses números. O WriteMessage termina num write() nesse descritor, a mesma chamada de sistema usada para escrever num arquivo.

A memória

O mapa guarda ponteiros. As goroutines do Daniel e do Mateus recebem o mesmo endereço e mexem na mesma Room. Com a struct guardada por valor, cada uma teria uma cópia, com um members e um mutex próprios, e uma não enxergaria a outra.

A chave de members é a conexão, não o alias. Cada conexão é um objeto único na memória, então duas pessoas nunca colidem, mesmo com o mesmo alias. E é exatamente o que o broadcast precisa para saber onde escrever.

A sala não guarda mensagens. Ela é uma lista de contatos. A mensagem passa pela goroutine de quem enviou e sai na hora, uma cópia por conexão. Quem entra depois não vê o que já foi dito.

O código

cmd/server/room.go
// Room tem seu próprio mutex: uma sala enviando não trava as outras
type Room struct {
	mu      sync.Mutex
	members map[*websocket.Conn]string // conexão -> alias
}

func (r *Room) join(conn *websocket.Conn, alias string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.members[conn] = alias
}

// leave remove a conexão e diz se a sala ficou vazia
func (r *Room) leave(conn *websocket.Conn) (empty bool) {
	r.mu.Lock()
	defer r.mu.Unlock()
	delete(r.members, conn)
	return len(r.members) == 0
}

func (r *Room) broadcast(myOwnConn *websocket.Conn, msg []byte) {
	r.mu.Lock()
	defer r.mu.Unlock()
	for c := range r.members {
		if c != myOwnConn {
			c.WriteMessage(websocket.TextMessage, msg)
		}
	}
}
cmd/server/main.go · handleWS
func handleWS(w http.ResponseWriter, r *http.Request) {
	conn, err := upgrader.Upgrade(w, r, nil)
	if err != nil {
		log.Println(err)
		return
	}
	defer conn.Close()

	// mensagem maior que o limite: o ReadMessage devolve erro, a gorilla responde com
	// close 1009 ("message too big") e esta conexão sai do loop e da sala como qualquer outra
	conn.SetReadLimit(maxMessage)

	// sem sala na URL (cliente antigo, outro programa): vai para a sala padrão
	name := cmp.Or(r.URL.Query().Get("room"), defaultRoom)
	alias := r.URL.Query().Get("alias")

	// entrar numa sala que não existe cria a sala
	mu.Lock()
	room := rooms[name]
	if room == nil {
		room = &Room{members: map[*websocket.Conn]string{}}
		rooms[name] = room
	}
	room.join(conn, alias)
	mu.Unlock()

	for {
		_, msg, err := conn.ReadMessage()
		if err != nil {
			break
		}
		// repassa a mensagem para os outros da mesma sala
		room.broadcast(conn, []byte(alias+": "+string(msg)))
	}

	// sai da sala; sala vazia deixa de existir, menos a padrão
	mu.Lock()
	if room.leave(conn) && name != defaultRoom {
		delete(rooms, name)
	}
	mu.Unlock()
}
09

Duas travas, uma ordem

O servidor tem dois níveis de sync.Mutex. A trava global mu protege só o mapa rooms e é usada para entrar e sair. A trava de cada sala, r.mu, protege a lista de membros e é a única que o broadcast usa. Assim, uma sala ocupada não atrasa as outras.

A regra que evita deadlock: sempre global primeiro, depois sala. Se uma goroutine travasse global→sala e outra sala→global, cada uma poderia segurar a trava que a outra espera, para sempre.

Por que entrar e sair usam a trava global: a sala fantasma

sem a trava global

joãoroom := rooms["dev"] → acha a sala
mateusleave → sala vazia → delete(rooms, "dev")
joãoroom.join(...) → entra numa sala que não está mais no mapa
✗ joão fica sozinho numa sala que ninguém mais acha

com a trava global

mateusmu.Lock · leave · delete · mu.Unlock
joãoesperando mu…
joãomu.Lock · rooms["dev"] é nil → cria sala nova · join
✓ as duas operações acontecem uma depois da outra

Resultado medido

latência na sala pequena · 50 mil pessoas na sala grande

O teste: 50 mil conexões numa sala recebendo 10 mensagens seguidas, enquanto duas pessoas numa sala pequena trocavam mensagens. Com a trava global, cada broadcast da sala grande segurava o servidor inteiro por centenas de milissegundos, e a sala pequena ficava na fila.

Com uma trava por sala, a barra verde quase não aparece no gráfico, e é esse o resultado. O detector de race condition do Go (go build -race) não encontrou problemas com 30 clientes entrando e saindo de 4 salas ao mesmo tempo.

Um detalhe: a trava de cada sala também garante a regra da gorilla de um escritor por conexão. Cada conexão pertence a uma única sala, e só o broadcast dessa sala escreve nela.

10

Quando alguém sai

Sair é o caminho de entrada ao contrário, e boa parte dele acontece sozinha.

  1. A conexão termina

    A pessoa aperta Ctrl+C, fecha o terminal ou a rede cai. O cliente devolve o terminal ao normal e fecha o socket (cliente por dentro).

  2. ReadMessage devolve erro

    A goroutine dessa pessoa no servidor, parada no ReadMessage, acorda com erro. O break sai do loop.

  3. leave e, se for o caso, delete

    Com a trava global: room.leave(conn) tira a conexão de members e diz se a sala ficou vazia. Se ficou, delete(rooms, name) apaga a sala.

  4. defer conn.Close()

    O handler retorna, e o defer agendado logo depois do upgrade fecha a conexão do lado do servidor.

  5. A goroutine termina

    Ela só existia para rodar esse handler. A pilha dela, de alguns KB, é liberada.

O cliente por dentro

O cliente é uma tela cheia, como o vim ou o htop: mensagens em cima, caixa de digitação embaixo. Quem desenha é o tview, uma biblioteca de widgets de terminal construída sobre o tcell. Tudo que é tview fica no pacote internal/ui. O main.go do cliente só conhece quatro funções.

As goroutines do cliente

main · loop de eventos do tviewprocessa teclas e a fila de atualizações, redesenhaRun()
leitura do terminaltcell lê o stdin em modo raw e gera eventos de teclaread(stdin)
recebimentoo go func() do main.goReadMessage()

Só o loop de eventos mexe na tela. Duas goroutines escrevendo no mesmo TextView ao mesmo tempo seria race condition. Por isso a de recebimento não desenha: o Print empacota a mudança numa função e usa QueueUpdateDraw para colocá-la na fila. O loop executa a função na vez dele e redesenha.

Só o loop de eventos escreve na conexão. O send é chamado no Enter, dentro do loop. Assim a regra da gorilla de um escritor por conexão vale também do lado do cliente.

Seguir o fim

O TextView do tview não acompanha texto novo por padrão. Quando a tela enche, as mensagens novas ficam escondidas embaixo até alguém rolar. Isso apareceu num teste ao vivo, quando a conversa passou de uma tela. Uma chamada a ScrollToEnd() na criação liga o "seguir o fim".

Com PgUp, o tview desliga o seguir, para dar para ler o passado sem ser puxado de volta a cada mensagem nova. Qualquer mudança na caixa de digitação chama ScrollToEnd() de novo.

Descer até o fim com PgDn não religa o seguir: é o jeito do tview. Digitar resolve.

Largura na tela, não bytes. StringWidth conta colunas: ã ocupa 2 bytes e 1 coluna, um emoji ocupa 2 colunas. A divisão pela largura da caixa dá quantas linhas cheias o texto ocupa. O +1 é a linha atual, onde o cursor está. O +2 são as bordas.

Quebra em qualquer caractere. A caixa usa SetWordWrap(false): quebrando só entre palavras, uma palavra longa pularia inteira para a linha de baixo e a conta deixaria de ser exata. Na caixa, "deplo" pode ficar numa linha e "y" na outra. Na área de mensagens, a quebra continua entre palavras.

Texto colado. Ele chega mais rápido que o redesenho, com a caixa ainda pequena, e ela rola por dentro para mostrar o cursor. Depois de crescer, SetOffset(0, 0) volta a rolagem para o topo. Sem isso, a primeira linha ficava escondida.

Saindo sem quebrar o terminal

Em modo raw, o terminal não ecoa o que você digita e o Enter não pula linha. Se o programa sai sem devolver o modo normal, a pessoa fica com um shell quebrado até digitar reset às cegas. Quem devolve é o Run(), ao retornar. Por isso nenhum caminho de saída pode pular o Run(), e o log.Fatal pula: ele chama os.Exit, que encerra o processo na hora.

Cores por alias

Hash do alias, não sorteio. O FNV-32a do alias escolhe uma de 12 cores. O mesmo alias tem a mesma cor em qualquer cliente, sem o servidor nem o protocolo saberem de cor nenhuma. Só o alias é colorido; o texto continua na cor normal.

Sua mensagem, em negrito. Vale para as linhas que você enviou, não para o alias. Se outra pessoa entra com o seu alias, ela aparece colorida, não em negrito: dá para notar.

Tags de cor viram texto. Para colorir, o tview passa a interpretar tags como [red]. Por isso tudo que vem de fora (alias, texto, nome da sala no título) passa por tview.Escape. Quem manda [red]oi aparece como [red]oi, literal.

O servidor manda alias: texto numa string só, e o cliente acha o alias cortando no primeiro ": ". Um alias com ": " dentro é cortado errado. Isso some quando as mensagens virarem estruturadas.

a paleta

#e06c75#e5a04b#d7c25a#98c379#4fd6a0#56b6c2#61afef#a3a0ff#c678dd#f08fc0#d19a66#7fb3d5

Tons médios, legíveis em terminal escuro e claro. Com 12 cores, colisões acontecem: numa sala com 5 pessoas, a chance de duas terem a mesma cor é de uns 60%.

Modo pipe por dentro

main · pipe()lê o stdin linha a linha, repete no terminal, enviaReadString()
leitura da salalê e descarta o que os outros mandamReadMessage()

Sem tela, sem tview: só duas goroutines. Uma é a única que escreve na conexão, a outra a única que lê. É a regra da gorilla de novo.

Por que ler o que não vai mostrar. As mensagens da sala continuam chegando para o pipe. Se ninguém lê, os buffers de rede enchem e o broadcast do servidor, que escreve para um membro de cada vez com a trava da sala, fica parado esperando por ele. A sala inteira trava.

Fim da entrada. Quando o ReadString devolve io.EOF, o pipe manda o frame de close do WebSocket e espera o servidor responder (até 2 s). Sair na hora poderia perder as últimas linhas.

O segundo caso é o limite "cliente lento atrasa a sala", agora medido. O cliente do teachat não cai nele porque sempre lê; um cliente mal escrito ainda derruba a sala. A correção de verdade é uma fila de envio por conexão no servidor.

cmd/client/pipe.go
// pipe é o modo sem tela (comando | teachat): envia cada linha do stdin para a sala,
// mostra a linha no terminal (como o tee) e sai quando a entrada acaba.
// Não abre a tela de propósito: num script ou no cron não tem ninguém para apertar Ctrl+C.
func pipe(conn *websocket.Conn) {
	// as mensagens da sala continuam chegando e precisam ser lidas, mesmo sem mostrar.
	// Sem isso, os buffers de rede enchem e o broadcast do servidor trava a sala inteira
	// esperando por nós. Esta goroutine é a única que lê; o pipe é o único que escreve.
	// readErr guarda por que a leitura parou. É escrito antes do close(done), então quem
	// vê done fechado já enxerga o valor certo (mesma garantia do "closed" no main.go).
	done := make(chan struct{})
	var readErr error
	go func() {
		for {
			if _, _, err := conn.ReadMessage(); err != nil {
				readErr = err
				close(done)
				return
			}
		}
	}()
	// a conexão caiu ou o servidor recusou algo (ex.: linha acima do limite, close 1009):
	// a escrita ainda "funciona" porque vai para o buffer, então quem avisa é a leitura
	dropped := func() {
		log.Fatal("connection closed: ", readErr)
	}

	// ReadString não tem limite de tamanho de linha (o bufio.Scanner para em 64 KB)
	r := bufio.NewReader(os.Stdin)
	for {
		line, err := r.ReadString('\n')
		if line != "" {
			line = strings.TrimRight(line, "\r\n")
			fmt.Println(line) // eco: você continua vendo a saída do comando
			// linha vazia aparece no eco, mas não vai para a sala
			if strings.TrimSpace(line) != "" {
				select {
				case <-done:
					dropped()
				default:
				}
				if err := conn.WriteMessage(websocket.TextMessage, []byte(line)); err != nil {
					// o motivo de verdade costuma chegar pela leitura (ex.: close 1009, linha
					// grande demais); espera ela um instante antes de mostrar o erro da escrita
					select {
					case <-done:
						dropped()
					case <-time.After(time.Second):
						log.Fatal("connection closed: ", err)
					}
				}
			}
		}
		if err == io.EOF {
			break
		}
		if err != nil {
			log.Fatal("error reading input: ", err)
		}
	}

	// fecha direito: manda o frame de close e espera o servidor responder (aí a goroutine
	// de leitura termina e fecha done). Sair sem isso pode perder as últimas linhas.
	conn.WriteMessage(websocket.CloseMessage, websocket.FormatCloseMessage(websocket.CloseNormalClosure, ""))
	select {
	case <-done:
		// fechamento normal (1000) é a resposta ao nosso close; qualquer outro é problema
		if !websocket.IsCloseError(readErr, websocket.CloseNormalClosure) {
			dropped()
		}
	case <-time.After(2 * time.Second):
	}
}

Todo o estado do servidor vive em memória. Medimos quanto isso custa abrindo milhares de conexões numa sala e lendo o VmRSS do processo em /proc.

São cerca de 17 KB por conexão, quase tudo pilha de goroutine e os buffers de 4 KB de leitura e escrita da gorilla. Os dados do chat (mapa, alias) somam poucas dezenas de bytes por pessoa. O tempo de broadcast cresce em linha reta, uns 6 µs por destinatário.

Banco de dados? Ainda não. O que está em RAM é o estado das conexões, que só existe enquanto o processo vive. O banco entra junto com o histórico de mensagens, provavelmente SQLite em Go puro, para continuar sendo um binário único.

Limitações e segurança

O teachat está em desenvolvimento inicial e propositalmente cru. Estes são os limites conhecidos hoje:

Sem criptografia

O tráfego é ws:// em texto aberto. No Wireshark dá para ler as mensagens. Use só em rede confiável até o TLS chegar.

Cliente lento atrasa a sala

O broadcast escreve para um membro de cada vez, com a trava da sala. Uma conexão que não lê segura a sala dela: medido, a sala travou em 2082 de 5000 mensagens. A solução é uma fila de envio por conexão.

Logs grandes inundam a sala

O modo pipe manda uma mensagem por linha. Um build de 5000 linhas são 5000 mensagens na tela de todo mundo.

Alias não é verificado

Qualquer um entra como --alias daniel. A senha vai proteger a sala, mas não prova quem é quem dentro dela.

Sem histórico

Mensagem enviada para sala vazia se perde, e quem entra depois não vê o passado. O modo pipe depende disso para registrar logs.

Qualquer origem

O servidor aceita WebSocket de qualquer origem, então uma página aberta num navegador da rede consegue conectar nele.
